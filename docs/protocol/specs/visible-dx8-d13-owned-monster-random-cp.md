# Visible D13 owned monster-death random CP reward

Status: OPEN, source-only. The configured random reward and selected D13 wire sequence are retained. The current bound death path changes session CP and sends success before saving Character; a following XP owner then correctly rejects the stale saved image. A kill, reward and later XP/query remain ordered distinct commits, not a single crash-atomic grant.

A private receipt issued only by the actual random reward branch binds the real Frame context, current admitted actor, killed monster, selected reward and exact preimage. Before any success output, the Store checks current owner/recovery and the continuation fence, bounds the native uint CP wallet, prepares the exact full Character image and native/holder publication, then holds the real Character coordinator lock through before-image validation, replacement, postimage confirmation and native/holder publication. Ambiguous/malformed CP keys or missing owners refuse without success or wallet changes. An uncertain replacement or postcommit output/observer failure fences recovery and the exact binding; it cannot roll back a committed wallet or clear a replacement. The bound path refuses pending experience-continuation markers until a real compatible owner exists. Unbound component behavior remains separate.

Required actual-owner tests: deterministic declared random policy inputs, a genuine lethal monster followed by XP with both awards in complete saved/native/current state, a real file lease refusal preserving files/native/output and committed monster death, and output loss after committed CP. No synthetic death token, success callback or positive journal. This source description is not a runtime, crash-atomicity or live-client claim.

The fixed last-hitter boss-family branch uses the same file/native/holder writer, but has a distinct private one-use policy receipt. The Store re-evaluates and matches the actual monster family, map, boss flag and complete selected reward before consuming it. The existing one CP update followed by the source invocation count of last-hitter messages is prepared before commit and sent only afterward. Random and boss awards occurring on one death are separate ordered transactions; neither combines them with each other or with XP into one crash-atomic operation.
