# Unbound native proficiency file safety

The native proficiency file has a four-byte signed count followed by exactly that many 20-byte little-endian DBProf records; fields remain full-width ID/level/experience/needed and one-byte previous level, with three opaque padding bytes. Bound ordinary profiles remain refused on these unconfigured file routes.

An unbound load requires the genuine reciprocal client/player/storage owner, snapshots and fences the actual physical map, validates a bounded complete file with nonzero unique IDs and exact length, closes the opened handle, then publishes one prepared map merge. Existing in-memory rows win for matching IDs. Invalid count, row, duplicate, ID, trailing or truncated file refuses without touching the map. Rooted save preflights the actual map and a complete bounded byte image before a locked atomic single-file replacement. Opened save prepares a complete ABI image and final witnesses before its first write, seeks to zero, writes the whole image, sets the exact length, flushes and closes the handle; its post-first-write I/O failures cannot be claimed atomic.

The single-file atomic replacement does not claim cross-process isolation, multi-file durability, or bound-profile saved evidence. The owner, storage, UID and raw map witnesses must still match at their respective final fences.

The rooted route captures its configured root string, resolved absolute directory and UID-derived file before caller map/comparer activity. Existing and missing target paths are checked for ordinary ancestors and leaf, and captured configuration/root/UID are revalidated immediately before final raw witnesses and write or publication. Opened helpers have no configured-path authority.
